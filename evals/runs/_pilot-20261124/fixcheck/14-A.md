| State | Heading | Hint | Body |
|---|---|---|---|

## Problems

**1. A failed load is shown as the empty state.** (state / honesty)
Original: `.catch((e) => { setLoading(false); toast.error(e.message); })` and `<Empty text="Oops! Nothing here yet 🙂" />`.
On failure `mail` stays `[]` and `loading` flips to `false`, so the only branch left is the empty one: a request that never succeeded is reported as "nothing here yet". The toast is gone in a few seconds, and after that the screen is indistinguishable from a genuinely empty inbox.
→ Direction: give failure its own state that stays on screen; the empty state belongs only to a successful load that returned zero results.

**2. A count is displayed while there is no count.** (state)
Original: `<h3>Inbox · {mail.length} messages</h3>`, with `useState<Mail[]>([])` and `useState(true)`.
The heading sits outside the `loading` branch, so during the fetch and after a failure it reads "0 messages", a number the page does not have yet, and one the user will read as a real answer.
→ Direction: render the count only after a successful load; loading and failure need worded states instead of a number.

**3. A capped list is presented as the total.** (counts / truncation)
Original: `{mail.length} messages` next to `fetch('/api/mail?limit=' + PAGE)`.
`mail.length` counts what came back, not what exists. At 20 the heading says "20 messages" whether the account has 20 or 500, and the hint's "up to 20" is the only clue that anything was cut.
→ Direction: a heading may only claim a count once the API supplies one; a partial list has to say it is partial and of what. That needs a real total, so this is also a code question (open question 1).

**4. The raw exception text goes on screen.** (error)
Original: `toast.error(e.message)`.
`e.message` is `TypeError: Failed to fetch`, `SyntaxError: Unexpected token < in JSON at position 0`, or a server `detail` carrying paths and class names. That is developer text, often English internals, with no object named and no next step. It is also the entire error copy for a page-level failure.
→ Direction: keep `e.message` in the log; the UI gets one fixed sentence that names what failed to load and the step that actually resolves it. One home for that sentence, not the exception.

**5. Load failure exists only as a dismissible toast.** (error / container)
Original: `toast.error(e.message)`.
A toast that auto-dismisses is the wrong container for a failure that leaves the page in a wrong state. Carbon's notification pattern says critical messages must not use timer-dismissed notifications, and toasts are capped at three lines. See <https://carbondesignsystem.com/patterns/notification-pattern/>. There is also no retry affordance anywhere in the component, so even a good sentence here would have no next step to point at.
→ Direction: page-level inline error that persists, with a retry control; toasts stay for confirmed, low-stakes results.

**6. The loading state has no words at all.** (state / accessibility)
Original: `loading ? <Spinner /> : …`
Nothing says what is loading, and there is no text or live region to announce it, so the spinner's disappearance is the only signal, and the heading silently changing from "0" to N is the only result announcement. WCAG 4.1.3 wants that status exposed to assistive tech; Cloudscape's loading copy style is a short phrase, no article, no sentence-ending period.
→ Direction: one short loading line naming the object, inside a `role="status"` / `aria-live` region.

**7. The hint explains the request, not the result.** (mechanism)
Original: `Showing up to {PAGE} messages.`
It describes the `limit` the client sends, so it is identical at 3 items, at 20 items, and on failure, and it never answers the only question a truncation note exists for: is this everything? It also pads the page with a sentence the user cannot act on.
→ Direction: delete it. If partial results still need a note, it must be derived from a real total and shown only when the list is actually truncated (ties to #3).

**8. The empty state gives no next step and does not name what is empty.** (empty state)
Original: `Oops! Nothing here yet 🙂`
"Here" names nothing; "yet" tells the user to wait while offering nothing to do; there is no way to refresh or change anything, and once the string is reused for failures (#1) it also stops being true. Empty states need state + next step; the software style file's own example is "No API keys yet. Create one to start making requests." (an illustration of the elements, not a proposal for this screen).
→ Direction: name the object (messages) and give the one action the product actually supports.

**9. Tone: interjection, exclamation and emoji in a work inbox, reused for failures.** (tone)
Original: `Oops! Nothing here yet 🙂`
"Oops" implies something broke, which is wrong for a success-with-zero-results state, and exactly wrong where this string is shared with a real failure. GitHub Primer's stated Don't is "Oops, some checks failed." (<https://primer.style/foundations/content/>). Emoji are banned in error and warning copy in the software style, and a 🙂 is also read aloud by screen readers as "slightly smiling face", so it adds noise in the one place the copy should be quiet.
→ Direction: drop the interjection, the exclamation and the emoji; an empty state can stay light through wording, not decoration.

**10. "1 messages".** (counts / grammar)
Original: `{mail.length} messages`, where the plural is hard-coded.
Any single-message inbox renders broken English, which is the first thing a new user sees.
→ Direction: a count-aware plural format (ICU `plural` or a shared helper), applied to every count string, not this one only.

**11. The same object has no stable name.** (consistency)
Original: `Inbox` (container), `messages` (items), `Nothing here yet` (no noun at all), and `mail` in the code and API.
The heading and the hint call the items "messages", the empty state calls them nothing, and the code and endpoint call the concept `mail`. If the product actually says "email", all three copy variants are off. The empty state is the one place a user most needs the noun.
→ Direction: settle one noun (message / email / mail) and use it in heading, hint, empty state and error; keep "Inbox" as the container's name only.

**12. The page heading doubles as the live count.** (structure)
Original: `<h3>Inbox · {mail.length} messages</h3>`
The one heading on the page changes text on every load, so heading-based navigation lands on a different title each time, and the count change is announced as a heading change rather than a status. This is a structural call, so it may be intentional.
→ Direction: stable heading plus a separate count or status line. Low priority, and worth confirming against whatever else this page renders.
