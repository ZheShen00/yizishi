# UI copy review — Inbox

Scope: user-visible strings only. Problems only, no rewrites.

## The heading count — `Inbox · {mail.length} messages`

- It reads as the inbox total, but the request is made with `limit=20`; at most the first 20 items are ever counted, so a user with more mail is shown a capped number presented as the whole.
- `{mail.length}` is interpolated with no pluralization: one item renders as "1 messages".
- Initial state is `mail = []`, so while `loading` is true the heading already asserts "0 messages" — a number stated as fact while it is still unknown.
- After a failed fetch `mail` also stays `[]`, so the heading permanently reports "0 messages"; the failure case is indistinguishable from a genuinely empty inbox.
- "messages" doesn't say total vs. unread — the number inbox users actually care about — and nothing in the string makes the count actionable.

## The hint — `Showing up to {PAGE} messages.`

- Duplicates the heading count in different words, and the two can disagree: the heading updates with state, while the number here is a literal derived from a constant.
- Surfaces an implementation constant (`PAGE`) as product copy. The sentence is generated from the fetch page size, so it silently rewrites itself whenever that limit changes and exposes pagination mechanics the user never asked about.
- "up to" never resolves: nothing says which 20 (newest? first page?), whether more exist, or how to reach them. There is no pagination or load-more copy anywhere in the component.
- Rendered unconditionally — while loading, and in the empty/error states — so it claims items are being shown when none are. It is false in three of four states.

## The empty state — `Oops! Nothing here yet 🙂`

- One string covers two unrelated situations: an inbox with no mail, and a load that failed. On failure it tells the user they have no mail, which is a false claim about their own data.
- "yet" implies mail is expected to arrive or that the account is new — wrong for an established inbox, and misleading after an error.
- "Oops!" announces a problem while the rest of the sentence denies one; the string contradicts itself and contradicts the toast.
- Register is out of step with the rest of the UI (cutesy exclamation + emoji); the emoji is announced by screen readers and renders inconsistently across platforms.
- No next step: no copy about retrying, checking the connection, or refreshing. After a failed load this is a dead end.

## The error toast — `toast.error(e.message)`

- Emits a raw exception string ("Failed to fetch", "Unexpected token < in JSON…", "500") — untranslated, developer-facing, no product voice and no error taxonomy.
- No context: the string by itself never says the inbox failed to load.
- `e.message` can be empty or absent, producing a blank or "undefined" toast.
- It is the only failure copy and it is transient. Once it disappears, the text left on screen is the empty state claiming the inbox is empty — the two messages disagree, and the survivor is the wrong one.
- There is no inline error copy in the section itself, so the error is tied to a component that may be dismissed or missed.

## Missing copy

- Loading has no text at all (`<Spinner />` only): no status message, no live-region announcement. Loading is conveyed purely visually, and the only readable text in that state is the incorrect "0 messages".
- Nothing states the list's order or freshness (newest first? last updated?), so "showing" is unqualified.

## Consistency (minor)

- Register and punctuation are mixed across the three strings: no terminator in the heading, a period in the hint, `!` plus an emoji in the empty state.
- The middot in `Inbox · 20 messages` is used as punctuation; screen readers may read it aloud or skip it inconsistently.
