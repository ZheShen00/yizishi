## 结论

- 测试和门禁**都要改**——现在这两处一个是红、一个是挂，不是「可能」。
- 但改法**不是**把 `关闭页面会中断` 换成 `同步中，请勿关闭页面`。这两处都把「一整句文案」当成了契约，这次改文案就是被它绊倒的；照抄新文案只是把下一次绊倒的时间往后推。
- `src/banner.ts` 的改动**不用回退**：新文案仍然满足门禁注释里写明的诉求（没同步完 → 提醒别关页面）。红的是断言写法，不是需求。

## 1. 现在的实际状态

| 位置 | 断言 | 改完文案后 | 原因 |
|---|---|---|---|
| `tests/banner.test.ts:3` | `toContain("关闭页面会中断")` | ❌ 红 | 新文案里没有这半句 |
| `tests/banner.test.ts:6` | `not.toContain("仍在同步")` | ✅ 绿（**假绿**） | `仍在同步` 四个字在整个文件里已经不存在了，这条断言对任何不含它的返回值都成立——`"出错了"`、`"同步中"` 都能过，等于什么都没测 |
| `smoke/gate.sh:3` | `grep -qF '关闭页面会中断' src/banner.ts` | ❌ `FAIL 关页提醒不在了`，exit 1 | 源码里已无此串 |

验证方式说明：仓库里没有 `package.json`／测试脚本，这台机器也没有可用的 bash（`bash` 落到 WSL 存根，未安装发行版），所以我是按 `String.prototype.includes` 和 `grep -F` 的语义，逐条核对了工作区（未提交）的这三处内容，不是 jest 实跑。这不影响结论：三条都是纯字面量匹配，通过/失败是确定的。

## 2. 为什么不用回退 `banner.ts`

门禁自己的注释写的是「没同步完时必须提醒别关页面」，这是**意图**；`grep -F '关闭页面会中断'` 只是意图的一种**实现**。新文案「同步中，请勿关闭页面」依然完成了这个意图，只是不再解释「关了会中断」这个后果。所以这次是实现被文案变更打穿，需求没变——该修的是实现。

反过来说，如果为了"让门禁绿"而去回退文案、或者去改第 1 行注释把旧词留在文件里，那是拿门禁的脆弱性反过来绑住产品文案，方向错了。

## 3. 怎么改

### 3.1 `tests/banner.test.ts` —— 钉行为，不钉整句

```ts
import { syncBanner } from "../src/banner";

// 钉行为不钉措辞：文案归产品/设计，测试守的是
// 「没同步完一定有提示、且提示的是别关页面；同步完一定没有提示」。
test("没同步完 → 提醒别关页面", () => {
  const banner = syncBanner(false);
  expect(banner).not.toBe("");          // 横幅确实在显示
  expect(banner).toContain("关闭页面");  // 且诉求是「别关页面」
});

test("同步完 → 横幅消失", () => {
  expect(syncBanner(true)).toBe("");    // 原来的 not.toContain("仍在同步") 永远绿
});
```

这两条断言的性质：改措辞、改语气、改标点都不会误报；把「别关页面」这层诉求删掉则一定红；`done` 分支从「任意非空也能过」收紧成「必须为空」。

**明确不选的一种改法**：`expect(syncBanner(false)).toEqual("同步中，请勿关闭页面")`。它能过，也能检测文案被误改，代价是以后产品改一个字就要动测试——而这次改动正是这个循环的第一圈。如果你们确实要锁死文案（法务/i18n 硬要求），那是另一种策略：用 snapshot 或把文案抽成导出常量再比对，并接受这个更新成本；不要用现在 `not.toContain` 这种半吊子写法。

### 3.2 `smoke/gate.sh` —— 锚诉求词，并且别让注释喂饱它

```bash
#!/usr/bin/env bash
# 门禁：没同步完时必须提醒「别关页面」。
# 1) 锚点用诉求词「关闭页面」，不用整句文案：改文案不误报，诉求被删必须红。
# 2) 先剔掉注释行：本文件第 1 行注释就含「请勿关闭页面」，
#    不剔的话，只要注释里留着这几个字，横幅文案被删光门禁照样是绿的。
set -u
grep -vE '^[[:space:]]*(//|/\*|\*)' src/banner.ts | grep -qF '关闭页面' \
  || { echo "FAIL 关页提醒不在了"; exit 1; }
echo ok
```

我按这套逻辑核过四种情形，行为是想要的：

- 新文案 + 旧词只留在注释 → 绿（该绿）
- 旧文案整句 → 绿（文案回滚不误报）
- 文案改成「同步中」、诉求词删光 → 红（该红）
- 提示只挪进注释 → 红（原版门禁在这里会误判为绿）

另外，门禁更根本的短板是它 grep 的是源码文本，分不清分支：把文案挪到 `done === true` 那一支，原版门禁照样绿。如果哪天门禁能调起测试脚本（有 `package.json` / test 命令之后），它的最佳形态就是「跑测试」，把「文案里有没有别关页面」交给上面那条用例，`grep` 这层可以整个删掉；现在仓库里没有测试入口，才只能做静态检查，分支正确性只能靠单测兜。

### 3.3 不用动的地方

- `src/banner.ts:1` 的注释（`没同步完时提醒「请勿关闭页面」`）和新文案一致，别顺手改。
- 两个测试的标题仍然准确（「提醒别关页面」「横幅消失」），只换断言即可。

## 4. 改完怎么验（红/绿双向）

1. 三处改完，跑测试 + 门禁，应全绿。
2. 再做一次**反向验证**：把文案临时改成 `"同步中"`（去掉关页诉求），**测试必须红、门禁必须红**，然后改回来。
   只做第 1 步的话，你分不清「门禁守住了需求」和「门禁只是不再误报」——这恰好是这次问题能潜伏下来的原因。

## 5. 需要你拍板的一件事（不影响上面的改法）

新文案把「关闭页面会中断同步」这个**后果**删掉了，只剩指令。这不是 bug，是产品取舍：

- 有意为之（更短、语气更直接、为了 UI 宽度或 i18n）：现在这版就发。
- 「让用户意识到关页面会中断同步」本身是要传达的信息：建议折中成 `同步中，关闭页面会中断同步` 或 `同步中，关闭会中断同步`——留住后果，又比原文短。

这个决定只影响 `src/banner.ts` 一行；第 3 节的测试和门禁改法在两种文案下都成立。

## 改动清单

1. `tests/banner.test.ts`：两条断言都换（第 3 行现红、第 6 行假绿）。
2. `smoke/gate.sh`：换锚点 + 剔注释行。
3. `src/banner.ts`：提交前确认第 5 节那个取舍，其余不动。
