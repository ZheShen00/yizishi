## 1. 什么时候用这份

信号（命中任意两条就用；只命中一条时，结合用户的话判断）：

- **代码 / 依赖（iOS）**：`Info.plist` 里以 `NSxxxUsageDescription` 结尾的键（`NSLocationWhenInUseUsageDescription`、`NSCameraUsageDescription`、`NSPhotoLibraryUsageDescription`、`NSContactsUsageDescription`、`NSMicrophoneUsageDescription`、`NSUserTrackingUsageDescription` 等）；`Localizable.strings`、`InfoPlist.strings`；目录里有 `.xcodeproj` / `.xcworkspace`。
- **代码 / 依赖（Android）**：`AndroidManifest.xml` 里的 `<uses-permission>`（尤其 `ACCESS_FINE_LOCATION`、`POST_NOTIFICATIONS`、`READ_CONTACTS`）；`res/values/strings.xml`、`res/values-zh-rCN/strings.xml`。
- **代码 / 依赖（跨端）**：React Native（`ios/` 和 `android/` 目录并存、`react-native-permissions`）；Flutter（`pubspec.yaml`、`lib/l10n/`、`permission_handler`）；uni-app（`manifest.json` 里的 `"permission"` 节点、`pages.json`）；Taro（`app.config.ts`、编译到多端的 `dist/`）。
- **代码 / 依赖（小程序）**：`app.json`（微信/支付宝/字节/百度小程序的全局配置文件，含 `"pages"`、`"window"`、`"tabBar"`）；`project.config.json`；按平台区分的模板文件后缀——微信 `.wxml`/`.wxss`/`.wxs`，支付宝 `.axml`/`.acss`/`.sjs`，字节跳动/抖音 `.ttml`/`.ttss`，百度智能小程序 `.swan`。
- **目录 / 文件名**：`ios/`、`android/`、`miniprogram/`、`onboarding/`、`permissions/`、`push/`、`subscribe/`。
- **界面里的词**：开屏、启动页、下拉刷新、上拉加载、授权、允许 / 不允许、推送、订阅消息、连续包月、自动续费、注销账号、未成年人模式、青少年模式、小程序码、弱网、离线、断网重连、面容 ID、指纹、深色模式、分享到朋友圈、转发给朋友。
- **用户的话**：「手机 App」「iOS / 安卓」「小程序」「App 审核被拒」「推送文案」「开屏广告」「IAP」「订阅」「上架」。

和别的行业重叠时：金融类 App / 小程序先按金融行业的合规硬约束，再叠这份的手机端长度与系统交互规则；医疗健康类 App 先按医疗行业的风险用语规则，这份只管端上的长度与系统交互部分（权限、推送、弱网）；面向未成年人的 App/小程序，未成年人模式相关文案和 `education.md` 一起查。

机器可检查的具体信号举例（命中其一即可判定为 iOS / Android / 小程序工程）：

```xml
<!-- iOS: Info.plist 里出现任意一个 NSxxxUsageDescription -->
<key>NSCameraUsageDescription</key>
<string>用相机扫描收据上的二维码</string>
```

```xml
<!-- Android: AndroidManifest.xml 里的权限声明 -->
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" />
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
```

```json
// 小程序: app.json 里出现 pages / window / tabBar 字段
{
  "pages": ["pages/index/index"],
  "window": { "navigationBarTitleText": "首页" },
  "tabBar": { "list": [{ "text": "我的", "pagePath": "pages/mine/mine" }] }
}
```

## 2. 语气和人格

- 一句话定调：比网页更短——手指点的，不是鼠标点的；屏幕比显示器小一个数量级，先满足"放得下"，再谈语气。
- 人称：C 端年轻向产品（社交、内容、工具类）用"你"；金融、政务、企业服务类小程序用"您"，和行业规则冲突时听行业的。全站只定一种，不要首页"你"、详情页"您"。
- 正式程度：核心交互文案（按钮、报错、权限说明、扣费提示）比网页更克制，不玩梗、不卖萌；营销 / 运营位（push、开屏、活动页）可以口语化、可以带一个 emoji，但**权限说明和扣费提示不能走营销腔**（见第 6、8 节），这是手机端区别于网页最大的尺度差异。
- 感叹号：push 标题、活动文案里可以有一个；核心交互文案（按钮、报错、确认框）不用。
- emoji：只用在运营位和 push（如「🎉 新功能上线」），不进按钮、报错、权限说明、确认框、状态标签——这些地方要能被读屏器清楚读出来，也不能让人分心去猜这是不是在推销什么。
- 和 `principles.md` 不同、要覆盖的地方：
  - `principles.md` 的按钮字数标准是「2–4 个字」；手机端更紧：底部 Tab 栏文字、悬浮操作按钮普遍要求 **≤4 个汉字**，不少机型实际只能稳定显示 2–3 字（超出要么两行挤压，要么被系统截断出省略号）。这是设计实践惯例，不是官方文件的强制条款，这份据此从紧要求，优先 2–3 字。
  - `principles.md` 没细分"系统控件文字"——手机端大量按钮是系统渲染的：iOS 系统权限弹窗的按钮文字（"允许""不允许"或"好""不允许"）、Android 运行时权限弹窗的按钮文字，这些字 App 改不了。能改的只有系统弹窗弹出**之前**自己写的说明（预授权 / pre-permission screen）和 `Info.plist` / `strings.xml` 里的用途说明字符串。审文案第一步先分清哪句是系统的、哪句是自己的，系统那句不用提修改意见。

## 3. 代表厂商和规范

| 厂商 / 规范 | 风格要点（能落到句子上的） | 出处 |
|---|---|---|
| Apple Human Interface Guidelines（Writing / Alerts / Notifications） | 弹窗标题用简短的多词短语而非单词，尽量一行；正文用完整短句，1–2 行内写完；按钮文字要具体到动作本身，只读按钮也能懂在选什么；语气可以直接甚至偏负面，但不许指责、评判或嘲讽用户 | <https://developers.apple.com/design/human-interface-guidelines/foundations/writing>、<https://developers.apple.com/design/human-interface-guidelines/components/system-experiences/notifications/> |
| App Store Review Guidelines 5.1.1(ii)（Purpose Strings） | 用途说明必须具体到"这项数据被用来实现哪个功能"，不能只复述权限名称或讲空泛的"更好体验"；一种受保护资源写一条独立说明；主动语态、陈述句、以句号结尾 | <https://developer.apple.com/help/app-review/guideline-reference/5-1-1-purpose-strings> |
| Apple App Store Subscriptions 指南（3.1.2） | 订阅购买页必须同屏展示：订阅名称与周期、提供的内容、清晰醒目的续费总价（续费价是页面上最突出的价格元素，分摊价可以标但要弱化）；免费试用要写清时长和试用结束后扣多少 | <https://developer.apple.com/app-store/subscriptions/> |
| Material Design 3 · Content design（Notifications） | 通知服务用户、不服务产品：精确、及时、可执行、有上下文；关键信息放句首，因为人是扫读不是精读；标题控制在 30 字符内、正文控制在 40 字符内，正文不要重复标题；慎用动态插入文本，尤其标题里 | <https://m3.material.io/foundations/content-design/notifications> |
| Google Play「Data safety」与「Prominent disclosure」政策 | 收集敏感数据前要有应用内的、独立于系统权限弹窗的"突出披露"：说明收集什么、为什么、是否能关闭，用户明确同意后才能继续，同意前不能预先勾选 | <https://support.google.com/googleplay/android-developer/answer/10787469>、<https://support.google.com/googleplay/android-developer/answer/11150561> |
| 微信小程序设计指南 | Toast 只用于轻量级成功提示，1.5 秒自动消失、不打断流程、**不能用于任何报错**；报错在表单顶部说明原因并标出具体哪个字段；加载时间长要给取消操作和进度条，不能让用户干等 | <https://developers.weixin.qq.com/miniprogram/design/> |
| 华为应用市场 / HarmonyOS 应用审核 | 申请敏感权限时要同步告知使用目的：权限名称、对应的具体功能、用途，形式可以是弹窗、蒙层、浮窗；首次启动时不要一次性申请和当前功能无关的权限。「未同步告知权限申请的使用目的」是开发者常遇到的驳回理由 | 审核指南：<https://developer.huawei.com/consumer/cn/doc/app/50104>（JS 渲染，本次没取到正文）；驳回原文为开发者转述：<https://blog.csdn.net/LFQP_/article/details/135204612>。同一要求见下一行工信部通知第（十）项 |
| 《个人信息保护法》第十七条（告知同意） | 处理个人信息前要用"显著方式、清晰易懂的语言"告知：处理者身份、处理目的和方式、信息种类和保存期限、用户可以怎么行使权利——这四项是隐私政策首次弹窗文案的最低内容要求 | <http://www.npc.gov.cn/npc/c2/c3083402/202108/t20210820_313088.html> |
| 工业和信息化部《关于进一步提升移动互联网应用服务能力的通知》（工信部信管函〔2023〕26 号） | 第（四）项：开屏和弹窗信息窗口要提供"清晰有效的关闭按钮"，不得频繁弹窗干扰用户，不得利用"全屏热力图"、高灵敏度"摇一摇"等易误触发的方式诱导用户操作；第（十）项：调用相册、通讯录、位置等权限时，同步告知用户申请该权限的目的；第（九）项：用简洁、清晰、易懂的方式告知个人信息处理规则，突出显示敏感个人信息的处理目的、方式和范围 | <https://www.gov.cn/zhengce/zhengceku/2023-03/02/content_5744106.htm> |
| 国家市场监督管理总局《网络交易监督管理办法》第十八条 | 自动展期、自动续费类服务，要在用户接受服务前、以及自动续费等日期前，"以显著方式提请消费者注意"，并由消费者自主选择；服务期内要提供显著、简便的随时取消或变更选项，不得收取不合理费用 | 国家市场监督管理总局令第 37 号：<https://www.moj.gov.cn/pub/sfbgw/flfggz/flfggzbmgz/202104/t20210423_357848.html>；第十八条 2025 年修改后的现行文本见《国家市场监督管理总局关于废止和修改部分部门规章的决定》：<https://www.moj.gov.cn/pub/sfbgw/flfggz/flfggzbmgz/202511/t20251106_527617.html> |
| Apple App Review Guideline 5.1.1(v)（账号注销） | 支持账号注册的 App 必须让用户在 App 内发起删除账号，删除整条账号记录和相关个人数据；只提供临时停用不算数；入口要好找，通常放在账号设置里；非强监管行业的 App 不能要求用户打电话、发邮件或走客服流程才能删除 | <https://developer.apple.com/support/offering-account-deletion-in-your-app/> |
| Google Play 用户数据政策（账号与数据删除） | 支持账号注册的 App 要在 App 内提供账号和数据删除入口；如果账号体系在网页端，也要提供可发起删除请求的网页链接并在应用商店详情页里公示 | <https://support.google.com/googleplay/android-developer/answer/13327111>（具体页面内容未逐字核实） |
| 小米 / OPPO / vivo 应用商店审核 | 三家应用商店上架审核均要求展示隐私政策链接、首次申请敏感权限前有独立说明，具体文案措辞要求未逐条核实，以各商店当期公示的开发者文档为准 | 小米：<https://dev.mi.com/>；OPPO：<https://open.oppomobile.com/>；vivo：<https://dev.vivo.com.cn/>（均未核实具体文案条款） |

## 4. 术语和叫法

| 用 | 不用 | 说明 |
|---|---|---|
| 点击 | 轻点、点按 | 第三方 App 自己的界面文案统一用"点击"；只有在还原 iOS/Android 系统级手势教程时才分别跟随官方中文叫法（iOS="轻点"，Android="点按"），见下两条 |
| 轻点（仅限苹果官方语境） | 点击、点按 | 苹果中文支持文档和 HIG 中文站用"轻点"对应"tap"；仿写 iOS 系统教程、还原苹果官方措辞时才用这个词 |
| 点按（仅限安卓官方语境） | 点击、轻点 | Android 开发者文档中文版用"点按"对应"tap"，"轻触"是触控大类的统称；仿写 Android 系统教程时才用 |
| 推送 / 通知 | 二者混用 | "推送"指触达机制（后端推了一条消息），"通知"指用户在系统里看到的那一条；系统设置页的权限开关永远叫"通知权限"，不叫"推送权限" |
| 小程序 | 轻应用、迷你程序 | 官方术语只有"小程序"，不要自创别名 |
| 小程序码 | 二维码 | 小程序专属的跳转码统一叫"小程序码"，和普通二维码分开指代，避免用户以为随便哪个码都能扫出小程序 |
| 连续包月 / 连续包年 | 只写"订阅"而不说明周期 | 产品名用"连续包 X"；法律意义上的关闭入口、扣费提醒统一用"自动续费"这个通用说法，两套叫法都要出现，不能只留产品名把扣费性质盖过去 |
| 自动续费 | 自动扣款、自动扣费 | 面向用户说的是"续费"这个结果，不是"扣款"这个动作；"自动扣款"容易被读成会在不知情下扣钱，刻意回避反而更可疑 |
| 注销账号 | 删除账号、停用账号 | 统一"注销账号"，这是不可逆操作的专有叫法；"停用"在很多 App 里是可恢复状态（如被封禁、主动冻结），和"注销"必须分开，不能混用造成用户以为还能找回 |
| 退出登录 | 登出、注销 | "退出登录"可逆（重新登录就回来）；中文里的"注销"只留给账号注销这一个不可逆动作，不要在退出登录的按钮或确认框里出现"注销"字样 |
| 授权 | 同意（指系统权限场景） | App 自己预先解释用"申请授权""需要你的授权"；系统弹窗按钮文字是系统控件，显示"允许""不允许"，App 的文案里不要编造一套自己的按钮词再去对应 |
| 个人信息 | 隐私信息、用户数据 | 合规文案统一"个人信息"（对应《个人信息保护法》用词）；"隐私信息"是口语说法、"用户数据"是技术说法，三个词在同一页混用会让用户分不清是不是在说同一件事 |
| 未成年人模式 | 少儿模式、儿童模式、家长模式 | 对齐《未成年人网络保护条例》的用词，和 `education.md` 一致；已经上线叫"青少年模式"且用户熟悉的产品，按项目术语表，不擅自改 |
| 深色模式 | 夜间模式、黑夜模式 | iOS/Android 系统设置里统一是"深色模式"，自家 App 的开关跟随系统叫法 |
| 面容 ID | 人脸识别、刷脸（苹果设备语境） | 苹果设备专指"面容 ID"（Face ID 的官方译名）；安卓设备没有统一品牌词，按各机型厂商叫法（如"人脸解锁"），不能笼统写"生物识别"糊弄过去——用户想确认的是具体用指纹还是刷脸 |
| 下拉刷新 | 下拉更新、刷新一下 | 统一"下拉刷新"，约定俗成的交互名词 |
| 弱网 | 网络不好、网速慢（状态标签） | 状态标签统一用"弱网"或"网络较差"；提示文案里可以说人话，但同一类提示全站只留一种说法 |
| 离线 | 没有网络、断网（和弱网混用） | "离线"指完全没有网络连接，和"弱网"（有网但差）是两种状态，触发条件和提示语都不一样，不能共用一句话 |
| 开屏（页 / 广告） | 闪屏、启动图 | 大陆中文产品统一叫"开屏"；"闪屏"更接近港台叫法，不用 |
| 小组件 | widget、桌面组件 | iOS/Android 官方中文文档用词一致，统一"小组件" |
| 分享 / 转发 | 二者混用 | 微信生态里"转发"专指发给好友或群，"分享"专指发到朋友圈或其他 App；按钮文字要对应真实去向，不能两个按钮都叫"分享" |
| 关注 / 订阅 | 二者混用 | 对公众号 / 账号用"关注"，对"订阅消息"功能用"订阅"，这是两套独立机制——用户关注了账号不代表会收到任何订阅消息，文案混用会造成误导 |
| 实名认证 / 实人认证 | 二者混用、统称"身份验证" | "实名认证"核验身份证信息，"实人认证"（人脸比对）是另一道独立的强验证；大额支付、提现等场景常常两步都要做，文案要说清在做哪一步 |
| 清除缓存 | 清理数据、清空数据 | 和"注销账号""退出登录"分开说清楚：清除缓存不会丢账号信息，确认框里要讲明这一点，避免用户误以为会连账号一起清掉 |
| 长按 | 按住、长按住 | 统一"长按"；"按住"更接近"touch and hold"的直译，两个词在同一处交替出现会让用户怀疑是不是两个不同操作 |
| 左滑 / 右滑 | 侧滑 | "侧滑"不说明方向，列表项的滑动删除、聊天气泡的滑动回复都要指明具体方向，不能用笼统的"侧滑"代替 |
| 未读 / 已读 | 新消息、已查看 | 这是一套固定的状态词，不要和"新消息""已查看"混着用；角标数字对应"未读"，点开后状态变"已读" |
| 私信 | 消息、聊天 | 一对一的站内信专指"私信"，和群聊、系统通知的"消息"分开；按钮/入口名要对应实际去向 |
| 草稿箱 | 草稿、未发布 | 保存未发布内容的集合页统一叫"草稿箱"，单条未发布内容本身叫"草稿" |
| 免打扰 | 静音、屏蔽通知 | 关闭某个对象通知提醒统一用"免打扰"，"静音"更容易和"设备静音/麦克风静音"混淆 |
| 拉黑 | 屏蔽、加入黑名单 | 面向用户的按钮统一用"拉黑"这个更直接的词，"屏蔽"容易和"屏蔽某类内容/广告"的功能混在一起 |
| 验证码 | 校验码、动态码 | 短信/语音收到的一次性数字统一叫"验证码"，不要在登录页和支付页用不同的词指同一样东西 |
| 一键登录 | 手机号一键登录、本机号码登录 | 运营商提供的免输验证码登录统一用产品侧简称"一键登录"，技术文档里的"本机号码校验"不进用户界面 |
| 会员 | VIP、贵宾 | 面向中文用户的付费身份统一叫"会员"，等级名（如"黄金会员"）可以用 VIP 之类的词，但基础身份名不要中英混用 |
| 版本更新 | 升级、更新迭代 | App 商店更新说明统一用"版本更新"或直接写"更新内容"，不用"升级"（容易和付费升级会员等级混淆） |

## 5. 按元素写

只写和通用写法不同的部分；通用的按钮/报错/空状态规则见 `principles.md`。

**按钮（Tab 栏 / 悬浮操作按钮）**
规则：Tab 栏文字 ≤4 个汉字，悬浮按钮 / 芯片按钮同样从紧到 2–3 字；危险操作的按钮写动作本身而不是"确定"，这条和通用规则一致，手机端更要守住因为空间更小。
例：Tab 栏「我的」不写「个人中心」；删除确认按钮写「仍要删除」不写「确定」。英文同理：Tab label "Profile" not "My Account Center"；destructive button "Delete anyway" not "OK".

**权限预授权（系统弹窗之前自己写的说明页 / 说明字符串）**
规则：说清楚"这个权限用在哪个具体功能上"，不是复述权限名，也不是讲笼统的好处；一种权限一条独立说明；一句话、陈述句、以句号结尾。这条直接对应 App Store Guideline 5.1.1(ii)，Android 侧同理（写在跳出系统权限弹窗之前的说明文案里，而不是系统弹窗本身）。
例（不合格 → 合格）：
- 「需要定位权限」→「用你的位置推荐附近门店，仅在使用本功能时获取」
- "To use your camera." → "Scan the receipt's QR code by pointing your camera at it."

**引导页 / 首次使用（onboarding）**
规则：3 页以内，每页一句话配一张图，不写使用说明书式的长段落；跳过按钮全程可见，不能等到最后一页才能跳过；别把要在权限预授权里说的话提前塞进引导页当铺垫。
例：「上传一张照片，AI 帮你改好光线」，不写「本产品基于深度学习算法为您提供智能图像增强服务」。英文同理："Upload a photo, we'll fix the lighting" not "This product leverages deep learning algorithms to provide intelligent image enhancement services."

**应用商店信息（名称 / 副标题 / 简介）**
规则：App Store 应用名称、副标题各限 30 字符；Google Play 应用标题限 30 字符、简短描述限 80 字符，超出的提交不上去。桌面图标下方、搜索结果列表里显示的名字还会再截短，把最重要的词放最前面。
例：App Store 名称「记账本 - 极简记账」不写「记账本 - 一款帮助你轻松管理个人财务和日常收支的智能记账应用」（超过 30 字符，提交不上去）。

**下拉刷新 / 加载 / 空状态 / 弱网 / 离线**
规则：五种状态各自独立，不能互相顶替；弱网和离线的触发条件和文案都要分开（见第 4 节术语表）。
例：
- 下拉刷新中：「正在刷新」（不用「加载中」，加载中是首次进入态）
- 弱网：「网络较差，内容可能加载不全」+ 重试按钮
- 离线：「没有网络连接，请检查后重试」+ 重试按钮
- 空状态（首次使用）：「还没有收藏，点个心试试」+ 主操作

**toast vs snackbar vs dialog**
规则：toast（iOS/Android 通用）只说结果，不带操作，出现后自动消失，不能用来报错（微信小程序设计指南明确写了这条）；snackbar（主要见于 Android/Material）可以带一个轻量操作（如"撤销"），仍然自动消失；dialog 用在必须用户做决定才能继续的场景（权限、删除确认、扣费提醒），不自动消失，按钮要写动作本身。错误信息一律走 dialog 或页面内联提示，不走 toast。
例：上传成功 toast「已上传」；删除后可撤回用 snackbar「已删除，撤销」；权限请求用 dialog。英文同理：toast "Uploaded"；snackbar "Deleted · Undo"；dialog 用完整句子 "Allow access to your contacts to find friends who are already using the app?"

**推送通知文案（push）**
规则：标题不加句尾标点，控制在系统不截断的长度内。Material 3 给的上限是标题 <30 字符、收起状态正文 <40 字符，正文不重复标题；标题被截断的部分展开通知后也看不到。iOS 没有公开的字数上限，锁屏预览同样会截断，按 Material 的上限从紧写，系统会自己加省略号，不用手动加。关键信息放句首；不插入会被截断的动态变量，尤其是标题里。小程序没有真正意义的"推送"：触达用户只能通过用户主动授权过的「订阅消息」，由具体业务事件触发，文案要贴合审核通过的模板，不能自行塞入营销内容。
例：「你关注的机型降价了」而不是「【重要通知】根据您的浏览历史，我们为您推荐以下降价商品，点击查看详情」（信息放太后面、是营销腔不是通知腔）。

**应用内购买 / 订阅文案（IAP / subscription）**
规则：购买页同屏展示续费价、周期、取消方式三项（见第 3 节 Apple 指南），续费总价是页面最突出的价格元素；确认续费 / 开通按钮写清楚会发生什么，不写笼统的"立即开通"。
例：「¥30/月，连续包月，随时在设置中取消」优于「立即解锁全部功能」。

**账号注销（见第 7 节高风险场景的完整要求）**
规则：入口文案用"注销账号"，不绕弯子藏进"账号与安全"三级菜单之后还换一个说法；注销前要完整列出后果（数据清空、不可恢复、关联的会员/余额如何处理）。英文同理用 "Delete account"，不用 "Deactivate account"（后者在 Apple/Google 的政策语境里专指可恢复的停用，和注销是两件事，见第 6 节）。

**手势动词**
规则：第三方 App 自己的界面、教程、空状态插图说明统一用"点击"；只有在原样引用或仿写系统级操作说明时，才跟随对应平台的官方中文叫法——iOS 用"轻点"（对应 tap）、"轻扫"（swipe）、"轻点并按住"或"长按"（touch and hold）；Android 用"点按"（tap）、"轻触"（touch，触控操作的统称）。同一个 App 内部，同一个动作（比如双指缩放）只固定一种叫法，不要图片说明写"双指捏合"、文字提示写"两指缩放"。英文产品文案统一用 "tap"，不用 "click"（click 是鼠标动作的残留词，iOS/Android 官方文案都已经统一成 tap）。
例：教程插图「长按图片保存到相册」；系统级帮助文档「轻点屏幕以唤出控制中心」（引用 iOS 官方说法时才这样写）。英文："Tap and hold the photo to save it"，不写 "Click and hold"。

**确认框（危险操作：退出登录 / 清除缓存 / 删除）**
规则：按危险程度分层——不可逆操作（删除、注销）要在确认框里写清楚后果和能否撤回；可逆操作（退出登录、清除缓存）只需说明会发生什么，不用营造紧张感。按钮写动作本身。
例：「清除缓存后需要重新加载图片和视频，不会影响你的账号数据」+「清除缓存」按钮；「退出登录后需要重新验证身份才能继续使用」+「退出登录」按钮。英文同理："Clearing cache won't affect your account data, but images and videos will need to reload." + "Clear cache"。

**状态标签（审核 / 认证类流程）**
规则：和 `principles.md` 的状态标签原则一致，但手机端常见的是审核类流程（实名认证、提现、发布内容），要用一套固定词覆盖"已提交但没结果"这个状态，不能用"处理中"模糊带过所有未完成态。
例：「审核中 / 已通过 / 未通过 / 已失效」，其中"审核中"和"未通过"必须分开，不能让用户以为没通过也是"还在等"。

**客服 / 帮助入口**
规则：涉及资金、账号安全、未成年人退款等场景，帮助入口要给出具体能做什么（如"申请退款""联系在线客服"），不要只写"帮助中心"或"联系我们"这类不说明能解决什么问题的笼统词。
例：「申请自动续费退款」优于「常见问题」。

**输入法 / 键盘上的操作按钮**
规则：软键盘右下角的 return 键文字要对应这一屏真正会发生的动作（发送、搜索、完成、下一步），不要全站统一写"完成"——聊天输入框应该是"发送"，搜索框应该是"搜索"，表单最后一项才是"完成"。这是 iOS/Android 输入框都暴露的一个可配置属性（`returnKeyType` / `imeOptions`），容易被整站套用一个默认值。
例：聊天输入框键盘右下角「发送」，不是「完成」；搜索框键盘右下角「搜索」，不是「前往」。

## 6. 合规和硬约束

必须出现的话、不许出现的话，以及对应出处：

- **隐私政策首次弹窗必须说清四件事**（《个人信息保护法》第十七条）：处理者身份、处理目的和方式、信息种类和保存期限、用户可以怎样行使自己的权利。四项缺一不可，不能只放一个"同意"按钮和一句"我们重视你的隐私"。<http://www.npc.gov.cn/npc/c2/c3083402/202108/t20210820_313088.html>
- **用户撤回同意、要求删除的权利必须有对应功能**（《个人信息保护法》第四十四、四十七条）：个人撤回同意后，处理者应当主动删除其个人信息；注销账号、关闭某项授权，不能是"申请了但系统不处理"。
- **不得打包索权、不得默认勾选、不得以拒绝非必要权限为由拒绝服务**（《App 违法违规收集使用个人信息行为认定方法》）：不能要求用户一次性同意打开多个可收集个人信息的权限，不同意就无法使用；不能用默认选中的勾选框代替明示同意；不能因为用户不同意收集非必要个人信息或开启非必要权限，就拒绝提供本来和这项信息无关的核心功能。（国信办秘字〔2019〕191 号，全文：<https://www.cac.gov.cn/2019-12/27/c_1578986455686625.htm>）。同一文件还把「进入 App 主界面后要点 4 次以上才能看到隐私政策」「文字过小过密、颜色过淡」认定为未公开收集使用规则，隐私政策入口和字号也要守这条线。
- **开屏和弹窗必须有清晰有效的关闭按钮，不得高频弹窗、不得用易误触发的"摇一摇"诱导跳转**（工信部信管函〔2023〕26 号第（四）项）：关闭按钮不能做成找不到或点不中的样子。<https://www.gov.cn/zhengce/zhengceku/2023-03/02/content_5744106.htm>
- **自动续费类服务必须在扣费前以显著方式提醒，并提供随时可取消的入口**（《网络交易监督管理办法》第十八条）：提醒不能用浅色小字或默认折叠的方式"合规但看不见"；取消入口要"显著、简便"，不能让用户只能靠联系客服取消。
- **iOS 权限用途说明必须具体到功能，不能只复述资源名或讲空泛好处**（App Store Review Guideline 5.1.1(ii)）；**订阅购买页必须同屏展示价格、周期、续费说明**（3.1.2）。
- **Android 侧收集敏感数据前要有独立于系统权限弹窗的应用内"突出披露"**（Google Play Data safety / Prominent disclosure 政策），同意前不能预先勾选。
- **支持账号注册的 App 必须同时提供账号注销，不能只给登出 / 停用**（Apple ASRG 5.1.1(v)；Google Play 用户数据政策的账号与数据删除要求），入口要能在 App 内直接触达，不能把"注销"包装成需要邮件申请才能办的隐藏流程。

没有法规硬约束、但属于行业惯例硬约束的：

- Tab 栏 / 悬浮按钮文字 ≤4 个汉字（见第 2 节），超出普遍会被截断或挤压成两行，不是"写得下就行"。
- 小程序没有系统级 push，只有用户主动授权过的「订阅消息」，营销内容不能借这个通道发送。
- Android 13 起通知权限（`POST_NOTIFICATIONS`）需要用户运行时授权；在系统弹窗之前最好有一屏自己的说明（说明用户会收到哪类通知、大概频率），直接跳系统弹窗、不给理由的拒绝率明显更高，这是平台惯例而非强制条款。

**三份要求叠加的地方**：隐私政策首次弹窗同时要满足三套来源——《个人信息保护法》第十七条的四项告知内容、《App 违法违规收集使用个人信息行为认定方法》对"默认勾选 / 打包索权 / 拒绝服务"的禁止、以及 App Store / Google Play 审核对用途说明具体性的要求。只满足其中一套（比如只顾着把四项内容都写上，却默认勾选了同意框）在任何一边都过不了，审这类弹窗要按三份一起核对，不能只套用其中一份的清单。

## 7. 高风险场景

未成年人相关的具体消费限额、时长管理条文请与儿童/教育行业的合规清单一起核对，这里只给手机端文案层面的要求。

**自动续费扣费前**：必写——服务名称、扣费金额和周期、扣费日期、取消方式；不许——用"限时优惠"等营销语盖过扣费金额、把取消入口藏在三级菜单里。
例：「明天将从你的账户扣除 ¥30，续费连续包月。可在"我的-订阅管理"随时取消」。

**账号注销**：必写——注销后会发生什么（数据清空、是否可找回、关联权益如何处理）、注销入口位置；不许——要求用户必须先联系人工客服才能发起注销（人工客服可以是辅助渠道，不能是唯一渠道）、用"休眠""冻结"模糊"注销"的不可逆性质。
例：「注销后，账号内的数据将被清空且无法恢复，已购买的会员权益不会退还。确认继续注销吗？」

**权限预授权（定位 / 相机 / 麦克风 / 通讯录）**：必写——这项权限对应的具体功能；不许——只写"为了提供更好的服务"、把多个权限的说明合并成一句话。
例：「允许访问通讯录后，可以从中添加好友」，不写「允许访问通讯录以提升体验」。

**未成年人模式**：必写——开启 / 关闭后分别限制或恢复了什么；不许——用容易被孩子自行关闭的轻巧措辞（如把关闭按钮写得和打开按钮一样随意）。

**开屏广告**：必写——清晰可点的关闭按钮文字或图标说明（哪怕只是"跳过 5"倒计时，也要明确可点）；不许——用"摇一摇体验惊喜"这类诱导跳转的措辞。

**实名认证 / 大额支付二次确认**：必写——当前在做的是哪一步验证、失败后下一步怎么办；不许——把"实名认证"和"实人认证"混着说，让用户分不清卡在哪一步。
例：「请完成人脸核验以确认是你本人操作，核验通过后即可完成付款」。

**支付确认（扣款前的最后一屏）**：必写——扣款金额、扣款对象（谁收钱）、支付方式；不许——用"确认"二字代替金额本身出现的位置，让用户看不到具体要付多少钱就点了确认。
例：「向"XX 旗舰店"支付 ¥128.00，使用微信支付」+「确认支付」按钮，不写孤零零一个「确认」按钮却不在同一屏显示金额。

**隐私政策更新通知**：必写——这次更新具体改了哪些实质内容（新增的数据类型、新增的第三方共享方）；不许——只写「隐私政策已更新，请查看」而不提示具体变化，等同于让用户重新读一遍全文才能发现哪里变了。
例：「隐私政策更新：新增与 XX 广告平台共享你的设备标识符，用于个性化推荐」。

**未成年人消费 / 使用限制提示**：必写——当前触发的是哪一类限制（时长、时段、单笔或月度消费限额）以及达到限制后会发生什么；不许——用笼统的「操作异常，请稍后再试」掩盖"这是未成年人保护机制触发的，不是故障"。国务院《未成年人网络保护条例》（国务院令第 766 号，2024 年 1 月 1 日起施行）对网络产品和服务提出了未成年人模式、时间管理、消费管理的要求（具体条号未核实）。
例：「根据未成年人模式设置，今日使用时长已达上限，将于明天 6:00 后恢复」。

## 8. 这个行业的 AI 腔和坏写法

| 坏写法 | 例子 | 改法 |
|---|---|---|
| 权限说明讲好处不讲用途 | 「开启定位，获得更智能的体验」 | 「用你的位置推荐附近门店」——写具体功能 |
| 系统权限弹窗里塞营销话术（弹窗文字其实是自己写的预授权页） | 「同意并继续享受专属服务」 | 「允许访问相册以选择头像」——说清楚干什么用 |
| 推送标题写成一整句话，被系统截断出省略号 | 「【重要通知】根据你的浏览记录，为你推荐了以下三款可能感兴趣的商品，点击立即查…」 | 「你关注的机型降价了」——关键信息放最前 40 字符内 |
| 自动续费提醒用小字 / 浅色字"合规但看不见" | 灰色 10px 小字写在购买按钮下方不起眼处 | 和价格同样大小、同一屏展示，不许靠视觉弱化藏起来 |
| 把"注销账号"包装成模糊词，降低用户警觉 | 「休眠账号」「暂别账号」 | 「注销账号」——不可逆操作用它本来的名字 |
| 默认勾选"已阅读并同意"协议 | 复选框默认打勾，用户不点就视为同意 | 默认不勾选，用户主动勾选才算同意 |
| 关闭按钮做成找不到或点不中的样子 | 几乎透明的小"×"藏在角落、倒计时结束前完全不可点 | 关闭按钮清晰可见、可点，倒计时只影响广告跳转不影响关闭 |
| "摇一摇"等诱导式跳转话术 | 「摇一摇解锁惊喜福利」 | 去掉摇一摇跳转这个机制本身，不只是改文案 |
| 空状态卖萌掩盖"什么都没有" | 「呀，这里空空如也呢～要不要去逛逛？」 | 「还没有收藏内容」+ 明确的下一步操作 |
| 打包索权说成一句笼统的话 | 「我们需要访问你的相机、相册、位置、通讯录以提供完整服务」 | 每项权限单独一条说明，用户可以分别决定 |
| 实名认证和实人认证混着说 | 「请完成身份验证」（用户不知道具体要做哪一步） | 「请完成人脸核验（实人认证）」——写清是哪一种 |
| 未成年人保护机制触发时伪装成故障 | 「操作异常，请稍后再试」（其实是时长限制生效了） | 「今日使用时长已达上限，明天 6:00 后恢复」——说明真实原因 |
| 同一动作在全站用不同手势动词 | 教程写"轻点"，按钮提示写"点击"，语音提示写"点一下" | 第三方 App 自身文案统一用"点击"，只有仿写系统教程才用平台官方词 |
| 支付确认页看不到具体金额 | 单独一屏只有一个大大的「确认」按钮，金额在上一屏 | 金额、收款方、支付方式和「确认支付」按钮同屏展示 |
| 隐私政策更新只说"已更新"不说改了什么 | 「隐私政策已更新，请查看最新版本」 | 「新增与 XX 广告平台共享设备标识符，用于个性化推荐」——写清具体变化 |
| 账号注销流程被设计成只能联系人工客服 | 「如需注销账号，请添加客服微信办理」 | App 内直接提供注销入口和流程，客服作为辅助渠道而非唯一渠道 |

## 9. 改前 → 改后

| 改前 | 改后 | 问题 |
|---|---|---|
| 「需要定位权限才能继续」 | 「用你的位置推荐附近门店，仅在使用本功能时获取」 | 只复述权限名，不说明具体用途，不满足 ASRG 5.1.1(ii) |
| "To use your location." | "Uses your location to recommend nearby stores while you're using this feature." | 用途说明不具体，App Store 审核会被打回 |
| 「立即开通，解锁全部功能」 | 「¥30/月，连续包月，随时在"我的-订阅"中取消」 | 没有价格、周期、取消方式，缺三项必要披露 |
| "Subscribe now to unlock everything" | "$4.99/month, auto-renews. Cancel anytime in Settings." | 同上，Apple 要求同屏展示价格和续费说明 |
| 「休眠账号」 | 「注销账号」 | 用模糊词替代不可逆操作的真实名称，属于暗模式 |
| 复选框默认勾选「我已阅读并同意《用户协议》」 | 复选框默认不勾选，用户需主动勾选 | 默认同意是认定方法明确禁止的"非明示方式征求同意" |
| 「我们需要相机、相册、位置、通讯录权限以提供完整服务」 | 分别在各自触发场景出现：「允许访问相机以拍摄头像」「允许访问通讯录以添加好友」 | 打包索权，用户无法单独拒绝某一项 |
| push：「【重要通知】根据您的浏览记录，为您推荐以下商品，点击查看更多精彩内容」 | push：「你关注的机型降价了」 | 标题过长会被截断，关键信息没放在前面，且是营销腔不是通知腔 |
| 开屏广告关闭按钮做成半透明小"×"，3 秒后才能点 | 关闭按钮清晰常驻，倒计时只影响广告本身是否自动跳转，不影响能否关闭 | 关闭按钮难以发现/点击，违反"提供清晰有效的关闭按钮"的要求 |
| 空状态：「呀，这里空空如也呢～」 | 「还没有收藏内容，点个心试试」 | 卖萌掩盖"现状+下一步"，和界面文案通用原则冲突，手机端空间小更要省字 |
| Tab 栏文字「个人中心」 | 「我的」 | 超过 Tab 栏 ≤4 字的惯例上限，实际会被截断或挤成两行 |
| 「请完成身份验证」（大额转账前） | 「请完成人脸核验（实人认证）」 | 没说清是实名认证还是实人认证，用户不知道接下来要做什么 |
| 「网络异常，请稍后再试」（离线和弱网共用一句） | 离线：「没有网络连接，请检查后重试」；弱网：「网络较差，内容可能加载不全」 | 离线和弱网是两种状态，触发条件不同，共用一句话会让用户误判问题出在哪 |
| "Deactivate account"（实际会删除全部数据） | "Delete account" + 确认框 "Deleting your account removes your profile and data. This can't be undone." | 停用和删除是两件事；Apple 明确只提供停用不满足 5.1.1(v)，按钮词要和真实结果一致 |
| 「如需注销账号，请添加客服微信办理」 | App 内「我的-账号与安全-注销账号」直接提供注销流程 | 把唯一注销渠道设成人工客服，变相提高注销门槛，不满足"App 内可直接触达"的要求 |
| 教程插图写"两指缩放"，文字说明写"双指捏合" | 全文统一用"双指缩放"或统一用"双指捏合"，只留一种 | 同一动作用两个词，读者要停下来确认是不是两个不同手势 |
| App Store 名称「记账本 - 一款帮助你轻松管理个人财务和日常收支的智能记账应用」 | 「记账本 - 极简记账」 | 超过 30 字符上限，提交不上去；最重要的词要放最前面 |
| 聊天输入框键盘右下角写「完成」（全站输入框统一套用系统默认值） | 聊天框写「发送」，搜索框写「搜索」，表单最后一项才写「完成」 | return 键文字要对应这一屏真正会发生的动作 |
| push "Don't miss out! Check out what's new in the app today 🎉" | "The phone you follow dropped to $699" | 标题超过 30 字符且没有信息，关键信息要放进句首 |

## 10. 审查时加查的项

- [ ] 权限预授权文案是否写明"具体用在哪个功能"，而不是复述权限名或讲空泛好处（对照 ASRG 5.1.1(ii)）；是否存在打包索权（一次性要求多个权限、不同意就无法使用任何功能）。
- [ ] 隐私政策首次弹窗是否同时满足 PIPL 第十七条（四项告知内容）、《App 违法违规收集使用个人信息行为认定方法》（不默认勾选、不拒绝服务）、应用商店审核三套要求，而不是只套用其中一份清单。
- [ ] 自动续费 / 连续包月的价格、周期、取消方式是否同屏可见，没有被弱化成小字；支付确认页是否和金额、收款方、支付方式同屏展示。
- [ ] 账号注销入口是否好找、是否只能通过人工客服触达、措辞是否用的是"注销账号"本身而不是模糊词；注销前的后果提示是否完整。
- [ ] push 标题是否会在系统截断长度内读完关键信息；是否出现了营销腔开头而不是通知腔。
- [ ] Tab 栏、悬浮按钮文字是否超过 4 个汉字；App 商店的名称、副标题、简短描述是否在约 30 字符内说清楚核心价值。
- [ ] 弱网、离线、空状态（首次 / 被清空 / 筛选无结果）三类状态的文案是否各自独立；toast 是否被用来报错。
- [ ] 开屏 / 弹窗的关闭按钮是否清晰可点，倒计时是否只影响广告跳转而不影响关闭本身。
- [ ] 手势动词是否全文统一（同一个动作不要一处"轻点"一处"点击"）；软键盘右下角按钮文字是否对应这一屏真正的动作（发送 / 搜索 / 完成）。

## 11. 台港市场差异

- 台湾：
  - 首次隐私弹窗按《個人資料保護法》第 8 条告知六项内容：业者名称、目的、类别、利用期间／地区／对象／方式、权利行使方式、不提供的影响。<https://law.moj.gov.tw/LawClass/LawSingle.aspx?pcode=I0050021&flno=8>
  - App 内购买数位内容，要排除 7 日解除权时，须经消费者事先同意（《通訊交易解除權合理例外情事適用準則》第 2 条第 5 款）。购买确认页要写明这一点。<https://law.moj.gov.tw/LawClass/LawSingleRela.aspx?PCODE=J0170012&FLNO=2&ty=L>
- 香港：在收集当时或之前，提供「收集個人資料聲明」，写明目的、可能转移给哪类人、是否必须提供、查阅及改正权（Cap. 486 保障資料第 1 原則第 (3) 款）。<https://www.pcpd.org.hk/chinese/publications/files/GN_picspps_c.pdf>
- 第 6 节里大陆的部分不适用台港：《App 违法违规收集使用个人信息行为认定方法》、工信部通知、《网络交易监督管理办法》。苹果和 Google 的平台要求照样适用。
- 小程序：台港没有微信小程序那套生态，主流通讯软件是 LINE（台）和 WhatsApp（港）。「小程序」「订阅消息」这类说法要改写成具体功能。
- 个资：台湾适用《個人資料保護法》，香港适用《個人資料（私隱）條例》（Cap. 486），不是大陆《个人信息保护法》。
